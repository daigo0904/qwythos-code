# Qwythos Code

手元のパソコンで動く、自律コーディングの相棒です。
お願いを日本語で書くと、自分でファイルを探し、読み、書き換え、テストを走らせて、結果を報告します。
**考えるのは手元のモデル**（Ollama 上の qwythos / qwen3 など）で、あなたのコードが学習に使われることはありません。

調べものが要るときだけ、外に出ます（→[ネットにつながる部分](#ネットにつながる部分)）。
出ていくのは検索の言葉と URL だけで、**ファイルの中身も会話の履歴も送りません**。
ログインが要るページは、あなたが手でログインした本物のブラウザで開きます
（→[ログインが要るサイトを読ませる](#ログインが要るサイトを読ませる)）。**パスワードは受け取りません。**
`--no-net` を付ければ完全に手元だけで動きます。

```
❯ テストが落ちてるので直して

✻ 6.2 秒考えました
● run_command(npm test)
  ⎿ 終了コード 1
● read_file(sum.js)
  ⎿ 3 行を読み込み
● edit_file(sum.js)
  ⎿ 1 か所を置き換え
● run_command(npm test)
  ⎿ 終了コード 0

sum.js の引き算を足し算に直しました。npm test は通っています。
```

## 必要なもの

- Node.js 20 以上
- [Ollama](https://ollama.com) が動いていること（`ollama serve`）
- モデル: `gemma4:26b`（無ければ、入っているものから自動で選びます）。18GB の空きが要ります。
  足りないときは `-m qwythos:latest`（7.4GB）に落としてください

**本体は Node の標準機能だけで動きます。**外から持ってきた部品は1つも使っていません。

`npm install` が要るのは、次の2つを使うときだけです。どちらも入れなければ、
**その道具が渡らないだけ**で、他はすべて動きます（呼べない道具をモデルに見せない、が方針です）。

| 入れるもの | 何のために | 入れないと |
| :--- | :--- | :--- |
| `typescript` | TypeScript / JavaScript の[意味検索](#意味でコードを探すlsp) | `find_symbol` が渡らない（Rust・C++ は別途の言語サーバーで動く） |
| `playwright` | [ログインが要るサイト](#ログインが要るサイトを読ませる)を読む | `browse` と `/login` が渡らない |

どちらも `optionalDependencies` なので、`npm install` は失敗しません。

## 使い始める

```bash
# どこからでも qwc で呼べるようにする
cd ~/コーディングCLI
npm link          # もしくは: alias qwc="node ~/コーディングCLI/bin/qwc.mjs"

# 作業したいフォルダで起動
cd ~/my-project
qwc
```

`❯` が出たら、そのまま日本語でお願いを書いて Enter。

## 一回だけ実行する

自動化やシェルスクリプトから使う形です。

```bash
qwc -p "README のタイポを直して" --yolo
```

`-p` では確認に答えられないため、書き換えまで任せるなら `--yolo` が要ります。

## 安全のしくみ

自律的に動くものなので、勝手に壊さないための歯止めを3つ入れてあります。

1. **作業フォルダの外は触れません。** 起動したフォルダより上には出られません（`--allow-outside` で解除）。
2. **書き換え・コマンド実行・ネット接続は、実行前に確認します。** 差分や検索語を見てから y / n を選べます。
   `a` を押すと、以後そのセッション中は同じ種類を自動で許可します。
3. **読むだけのコマンドは確認なしで通します。** `ls` `cat` `git status` などの安全な一覧だけが対象で、
   `;` や `|` や `>` が混ざっていたら安全とはみなしません。

> **2026-08-06 に直した不具合。** それまで道具すべてが「確認なし」の設定になっていて、
> ここに書いた確認が**一度も出ていませんでした**（確認のしくみ自体は完成しているのに、呼ばれていなかった）。
> 書き換えもコマンド実行も、黙って実行されていました。
> 同じことが再発しないよう、道具ごとの設定値を検証（`npm test`）で固定してあります。

### 確認をどこまで飛ばすか、3段階から選べます

毎回すべてを聞かれると煩わしく、かといって全部飛ばすと無防備になります。間を用意しました。

| | 書き換え | コマンド実行・ネット | 使いどころ |
| :--- | :---: | :---: | :--- |
| 既定 | 確認する | 確認する | 初めてのプロジェクト |
| **`--accept-edits` / `/accept`** | **通す** | **確認する** | **ふだんの作業** |
| `--yolo` / `--dangerously-skip-permissions` | 通す | 通す | 中身を分かっている作業だけ |
| `--confirm` / `--no-yolo` | 確認する | 確認する | 既定を「通す」にしてあるときの、その回だけの打ち消し |

**書き換えだけを通す理由。** うるさいのはほぼ書き換えの確認ですが、そこは
[書いた中身が画面に出る](#書いた中身が画面に出ます)ので、後から目で追えます。
一方コマンド実行とネットは、**戻せないものを含むうえ、事前には何が起きるか画面から分かりません**。だから聞き続けます。

`--accept-edits` でも、`;` `|` `>` が混ざったコマンドは確認します。安全なコマンドの判定は3段階すべてで同じです。

> **`/save` で次回以降の既定にできます。**`--accept-edits` も `--yolo` も保存されます。
>
> **`--yolo` を保存すると、以後ずっと無防備です。**それでも忘れて事故らないよう、2つ用意してあります。
> 起動のたびに「確認なしモードです（保存された設定）」と警告が出るので、**なぜ確認が出ないのかが必ず分かります**。
> 危ない作業のときは **`--confirm`（`--no-yolo`）でその回だけ確認ありに戻せます**。設定はそのまま残ります。

## 起動オプション

```
-p, --print <文>       一回だけ実行して終了
-m, --model <名前>     使うモデル（既定: gemma4:26b）
    --host <URL>       Ollama の場所（既定: http://localhost:11434）
    --ctx <数>         文脈の広さ（既定: 32768）
    --temp <数>        創造性の高さ 0〜1（既定: 0.3）
    --steps <数>       1回のお願いで許すツール実行の上限（既定: 200）
    --yolo             確認を全部飛ばす（--dangerously-skip-permissions も同じ）
    --confirm          その回だけ確認ありに戻す（--no-yolo も同じ）
    --accept-edits     書き換えだけ確認なしにする（コマンドとネットは確認する）
    --no-think         思考モードを切る（--effort off と同じ）
    --effort <段階>    考える深さ（off / low / medium / high・既定 medium）
    --show-thinking    考えている内容を全部表示
    --quiet-thinking   考えている様子を非表示
    --cwd <フォルダ>   作業フォルダを指定
    --allow-outside    作業フォルダの外も触れるようにする
    --no-net           ネット接続を切る（検索とページ取得の道具を渡さない）
    --plan             計画モードで始める（まず調べて方針を出す。書き換えない）
    --chat             雑談モードで始める（普通に話す。書き換えない）
    --embed            別のアプリのエンジンとして動く（道具の実体は相手が持つ）
    --resume [ID]      前の会話の続きから
    --sessions         保存済みの会話を一覧
```

## 道具（ツール）

小さいモデルは選択肢が多いほど迷うので、数を絞っています。手元に6つ、外に4つ、段取りに4つ。
このうち実際に渡すのは、**そのとき呼べるものだけ**です（言語サーバーが無ければ `find_symbol` は渡しません）。

| 道具 | 役割 | 確認 |
| --- | --- | --- |
| `read_file` | ファイルを行番号つきで読む | なし |
| `list_dir` | フォルダの中身を見る | なし |
| `search_files` | 正規表現で横断検索（ripgrep があれば使用） | なし |
| `write_file` | ファイルを新規作成・全書き換え | あり |
| `edit_file` | ファイルの一部を厳密一致で置き換え | あり |
| `run_command` | シェルコマンドを実行 | 読み取り系以外はあり |
| `web_search` | ネットで調べる（Tavily） | あり |
| `web_fetch` | ページを1枚読んで文章にする | あり |
| `browse` | ログイン済みのブラウザでページを開く | あり |
| `todo_write` | やることリストを作る・進める | なし |
| `find_symbol` | 名前の定義・参照・型を意味で引く（LSP） | なし |
| `spawn_agent` | 調べものを別のエージェントに任せ、答えだけ受け取る | なし |
| `read_skill` | 置いてある手順書を読む（手順書があるときだけ渡す） | なし |
| `browser_login` | ブラウザを開いて、あなたが手でログインする | あり |

### 文脈の広さ

既定は **32,768トークン**ですが、これは**モデルの限界ではなく既定値**です。
`qwythos:latest` 自体は 1,048,576 まで扱えます。`--ctx 131072` のように広げられます。

広げれば大きなコードベースも読めますが、**そのぶん確実に遅くなります**。
会話は毎ターン丸ごと送り直すので、文脈が広いほど前処理の時間が積み上がります。
先に試すべきは、広げることより **`spawn_agent` に調べさせて答えだけ受け取る**ことです
（実測で、本体に残る文脈は3分の1以下になりました）。

## 意味でコードを探す（LSP）

`search_files` は文字の一致しか見ません。`renderTodos` を探すと、**コメントに書かれた説明文まで当たります**。
`find_symbol` は言語サーバーに聞くので、その名前が実際に何を指すかを分かったうえで答えます。

```
❯ renderTodos がどこで定義されて、どこから使われているか調べて

● find_symbol({"name":"renderTodos","operation":"definition"})
  ⎿ 1 件
● find_symbol({"name":"renderTodos","operation":"references"})
  ⎿ 4 件

renderTodos は src/ui.mjs の 177 行目で定義されています。
使用場所は src/tools.mjs:934 と bin/qwc.mjs:632 です。
```

このリポジトリで実際に比べた結果です。

| | 当たった件数 |
| --- | --- |
| `search_files`（文字で探す） | 7件（**うち2件はコメント内の記述**） |
| `find_symbol`（意味で探す） | **4件**（本物の参照だけ） |

**遅いモデルほど効きます。** 候補から本物を選ぶ作業が要らなくなるぶん、往復が減ります。

`operation` は3つ。`definition`（定義の場所）／`references`（使われている場所）／`hover`（型と説明）。
渡すのは**名前だけ**です。行番号と桁をモデルに数えさせると1文字のズレで別物を指すので、位置の特定はこちら側でやります。

### 用意するもの

言語サーバーが要ります。**入っていない言語では道具そのものを渡しません。**

| 言語 | 入れ方 |
| --- | --- |
| TypeScript / JavaScript | `npm i -g typescript-language-server` |
| Rust | `rustup component add rust-analyzer` |
| C / C++ | `brew install llvm`（clangd） |
| Python | `npm i -g pyright` |
| Go | `go install golang.org/x/tools/gopls@latest` |

追加のライブラリは要りません。LSP は「ヘッダ＋JSON を標準入出力でやりとりする」だけの決まりごとなので、
`src/lsp.mjs` に素で書いてあります。

> **TypeScript 7 には `tsserver.js` がありません。** グローバルに TS7 が入っていると、
> あるように見えて動きません。qwc は自前の `node_modules` に 5.x を持っていて、
> 作業フォルダに無ければそちらを使います。

## 調べものを別のエージェントに任せる

「この機能がどこにあるか探して」を本体にやらせると、**読んだファイルの中身がそのまま会話に残ります**。
32k の文脈は数ファイルで埋まり、肝心の作業に入る前に要約が始まります。

`spawn_agent` は、その調べものを別のエージェントに投げます。
読んだファイルは向こうの会話にだけ溜まり、**本体に返ってくるのは答えの数行だけ**です。

```
❯ 実行前の確認をどこで決めているか調べて、そのうえで直して

● spawn_agent(実行前の確認が要るかどうかを、どのファイルのどこで決めているか)
┌ 調べてきてもらいます
│ ● search_files(approval:)
│ ● read_file(src/tools.mjs)
│ ● read_file(src/agent.mjs)
└ 3 回調べて戻りました
```

任された側の出力は `│` で一段下げます。誰がしゃべっているのか分からないまま道具の実行が流れると、
**本体が勝手なことを始めた**ように見えるからです。

### 実測（同じ問い・`qwythos:latest`・このリポジトリ）

「`src/tools.mjs` で、実行前の確認が always になっている道具を全部挙げて」を解かせた結果です。

| | 所要 | 本体に残った文脈 | 本体が読んだ token | 答え |
| :--- | ---: | ---: | ---: | :--- |
| 自分で読む（1回で読み切ろうとした） | 276秒 | 15,897文字 | 9,607 | **6つ中2つ**（誤り） |
| 自分で読む（7回に分けて読んだ） | 135秒 | 12,945文字 | 32,467 | 6つとも正しい |
| **任せる（`spawn_agent`）** | 164秒 | **4,351文字** | **5,058** | 6つとも正しい |

**本体に残るのは3分の1以下**です。差はこのあと効いてきます。会話は毎ターン丸ごと送り直すので、
残った文脈は最後まで払い続けることになるからです（`5,058` と `32,467` の差がそれです）。
所要時間はほとんど変わりません。任された側も同じモデルを使うので、**手間が消えるわけではなく、置き場所が変わります**。
上の数字はモデルが常駐している状態のものです（1ファイル調べて答えるだけなら、任せて戻るまで通しで56秒でした）。
読み込みからだと数分待たされますが、それは任せたかどうかとは関係ありません。

上の1行目は、45KBのファイルを一度に読もうとして**切り詰めに気づかないまま**前3分の1だけで答えた例です。
省略の断り書きを「**これは全部ではない**」と分かる書き方に直しました（→[長すぎる出力の切り詰め](#モデルの癖への対処)）。

任された側は**読むことしかできません**。書き換える道具は最初から渡していません。
2つのエージェントが同じファイルを同時に書いたら、どちらの結果も信用できなくなるからです。
`spawn_agent` 自身も渡していないので、入れ子には広がりません。

立場が違うので、**指示文ごと差し替えています**。本体の指示には「変更したファイルを報告せよ」が入っていて、
何も変更できない相手にそれを渡すと、変更していないのに変更したと書いて戻ってきます。

> **小さいモデルは自分からは使いません。** 実測では、頼まない限り自分で読みにいきました。
> 「別の担当に任せて」と日本語で頼んでも自分でやってしまいます。
> **`spawn_agent` という名前を出して**頼んだときだけ、確実に任せました。

## 使ううちに覚える（`/refine`）

毎回まっさらから始めると、同じ発見を毎回やり直します。`/refine` を使うと、
**いまのやり取りを見直して、覚えておく価値のあることだけを書き留めます。**

```
❯ このフォルダのテストを走らせて、結果を教えて。
  （list_dir で探してから node test_cart.js を実行）

❯ /refine テストの走らせ方を覚えておいて

  + [このフォルダ] テストは node test_cart.js で実行できる。
```

次からは、探す手間が消えます。**同じ問いで実測した差**です。

| | 道具を使った回数 | 時間 |
| --- | ---: | ---: |
| 覚え書き無し | 2回（`list_dir` → `run_command`） | 8.5秒 |
| **覚え書き有り** | **1回**（いきなり `run_command`） | **3.6秒** |

- `/refine list` — いま覚えていることと、その根拠を見る
- `/refine undo` — 直前の見直しを取り消す（当てる前の控えから戻します）

置き場は2つです。`.qwythos/harness.json`（この作業フォルダだけ）と
`~/.qwythos-code/harness.json`（どの作業でも）。

### 何でも覚えさせないこと

覚えたことは**毎ターンの入力に必ず乗ります**。つまり固定費です。
際限なく足すと、当たらない思い込みのために本来の作業の枠が削られていきます。そこで線を引いています。

- **ファイルの中身や関数の説明は覚えません。**読み直せば1回で済むことに、永久に払い続ける意味がないためです
- やり取りに出ていないことは覚えません（推測・一般論・元からある決まりごとの言い直し）
- 覚えるのは12件まで。1件200文字まで。超えたら古いものから落とします
- **ほとんどの回は「覚えることなし」が正しい答え**です。実際、ただ質問しただけの回では何も記録しません

> **考え方の出どころ。** [prime-agent](https://github.com/PrimeIntellect-ai/prime-agent)（MIT）の
> Continual Harness から借りました。コードは持ってきていません。借りたのは次の4つです。
> **基礎の指示文は絶対に書き換えない**（覚えたことは別の層として足すだけ）／
> 直すときは小さな追加・修正・削除にとどめる／1件ずつ根拠を持たせる／当てる前の控えを残して戻せるようにする。
>
> あちらは「モデルが書いた Python を常駐の REPL で実行する」設計で、シェルもファイル操作もその中で行います。
> qwc はそこには寄せていません。持ってきたのは**覚え方の作法だけ**です。

### 覚え書きは決まりごとより弱い

指示文では、覚えたことを「手がかりであって決まりではない」と伝えています。
ファイルの実物と食い違ったら、**ファイルを信じて、食い違いを報告する**ようにしてあります。
`QWYTHOS.md` の決まりごとは、覚え書きより後ろに置いてあるので、常にそちらが勝ちます。

## 手順書（スキル）とフォルダごとの決まりごと

どちらも「**必要になった時点で渡す**」という同じ考え方です。
最初から全部を指示文に積むと、使わないぶんまで毎ターン払うことになります。

### 手順書（スキル）

`.qwythos/skills/<名前>/SKILL.md` に置くと、**モデル自身が必要に応じて読みにきます**。

```markdown
---
name: release
description: リリース手順。版を上げてタグを打つまで
---
1. package.json の version を上げる
2. npm test が通ることを確認する
3. git tag v<版> を打つ
```

コマンド（`/名前`）との違いは、**誰が呼ぶか**です。
コマンドは人が呼びます。スキルは、人が「リリースして」としか言わなくても、
手順書があることに気づいてモデルが読みにきます。

指示文に載るのは**名前と一行の説明だけ**です。中身は `read_skill` で読みにきたときに渡します。
`~/.qwythos-code/skills/` に置けば、どのプロジェクトでも使えます（同じ名前なら作業フォルダ側が勝ちます）。

### フォルダごとの決まりごと

大きなリポジトリでは、場所によって作法が違います。
`src/` は TypeScript、`migrations/` は手で触らない、`docs/` は日本語で書く。

これを全部いちばん上の `QWYTHOS.md` に書くと、**触りもしないフォルダの作法まで毎回送る**ことになります。
そこで、**そのフォルダの `QWYTHOS.md` は、そこのファイルを触ったときに渡します**。

```
❯ src/api/handler.ts を直して

● read_file(src/api/handler.ts)
  ⎿ 84 行を読み込み
    （src/api/QWYTHOS.md の中身がここで一緒に渡る）
```

- 触ったファイルのフォルダから、作業フォルダまで上りながら集めます
- **近いフォルダのものほど後ろ**に置きます（指示は末尾にあるものほど効くため）
- 同じものは**1回しか渡しません**。毎回付けると同じ文が会話に積もります
- いちばん上の `QWYTHOS.md` はここでは渡しません（最初から指示文に入っているため）

### 書き換えたあとに走らせる

`.qwythos/hooks.json` を置くと、ファイルを書き換えた直後に走ります。

```json
{ "afterEdit": "npx prettier --write \"$QWC_FILE\"" }
```

対象のファイルは `$QWC_FILE`（絶対パス）と `$QWC_FILE_RELATIVE` で受け取ります。

**失敗しても作業は止めません。出力をそのままモデルに返します。**
直せるのはモデルなので、こちらが握りつぶすと直す機会そのものが消えます。

```
● edit_file(src/app.ts)
  ⎿ 1 か所を置き換え
    [afterEdit hook failed (exit 1)]
    src/app.ts:12:5 - error TS2322: Type 'string' is not assignable to type 'number'.
    Fix what it reported before moving on.
```

## 外の道具をつなぐ（MCP）

同梱の道具はファイルとネットとブラウザだけです。
データベースを引く、社内のAPIを叩く、といったことはできません。
**MCP** は、そういう道具を別のプログラムとして用意してつなぐための決まりごとです。

作業フォルダの `.qwythos/mcp.json` に書きます。

```json
{
  "servers": {
    "sqlite": {
      "command": "uvx",
      "args": ["mcp-server-sqlite", "--db-path", "./app.db"],
      "tools": ["read_query", "list_tables"]
    }
  }
}
```

道具は `mcp__sqlite__read_query` のような名前で渡ります。
どこの道具か名前で分かるようにしてあります（使えなくなったとき、どちらの話か説明できないと困るため）。

### 道具を増やしすぎない

**ここがいちばん気をつけたところです。**

MCP のサーバーは、1つで20個も30個も道具を持っていることがあります。
それを全部見せると、**手元の9Bは選べなくなります**。qwc が同梱の道具を絞っているのと真っ向からぶつかります。

そこで `"tools"` に書いたものだけを渡します。
書かなければ、そのサーバーの**先頭から8個まで**です。**全部渡す方法は用意していません。**
用意すると、いちばん効く歯止めが外れます。

### 外の道具は必ず確認します

何をする道具かは、こちらには分かりません。ファイルを消す道具かもしれません。
分からないものを黙って走らせないので、**実行前に必ず y/n を聞きます**（`--yolo` を除く）。

つながらないサーバーがあっても、理由を出して他は続けます。
コマンド名を1文字書き間違えただけで本体が落ちるのは割に合わないので、そこは拾ってあります。

## 別のアプリの中でエンジンとして使う（`--embed`）

qwc の値打ちは、道具そのものではなく**輪のほう**にあります。
考える→道具を使う→結果を見る、の繰り返しと、そこに積んだ受け皿
（本文救済・促し・やることリスト・計画モード・調べものの委譲）が中身です。

ところが、これを別のアプリに入れようとすると道具で行き詰まります。
入れる先にはたいてい**自前の作法**があり、qwc が自分で `fs.writeFileSync` を呼んだ時点でその約束は破れます。

そこで `--embed` では、**道具の実体をぜんぶ相手に返します**。
qwc は「`read_file` をこの引数で呼びたい」と言うだけで、実際に読むのは相手のアプリです。

| | どちらが持つか |
| :--- | :--- |
| 輪・指示文・受け皿・やることリスト・調べものの委譲 | **qwc** |
| 道具の実体・権限・記録 | **相手のアプリ** |

行ごとの JSON を標準入出力でやりとりします（JSON Lines）。追加のライブラリは要らず、どの言語からでも読めます。

```
相手 → qwc   {"type":"hello","tools":["read_file","list_dir"],"root":"/path","model":"qwythos:latest"}
相手 → qwc   {"type":"user","text":"担当者の名前を全部調べて"}
qwc  → 相手  {"type":"tool_request","id":"t1","name":"list_dir","args":{"path":"."}}
相手 → qwc   {"type":"tool_result","id":"t1","output":"売上4月.md\n売上5月.md","isError":false}
qwc  → 相手  {"type":"turn_end","text":"佐藤さんと鈴木さんです。"}
```

- **相手が `hello` で名乗った道具だけをモデルに見せます。** 相手が持っていない道具を見せると、
  モデルは呼んで断られ、その理由を考えるのに往復を1回使います
- `todo_write` と `spawn_agent` は外に触れないので、**相手の実装が要りません**。輪と一緒に付いていきます
- 確認は持ち主の仕事なので、こちらでは聞きません（同じことを二度聞かれないため）
- 画面表示は**標準エラー**に寄せます。標準出力に1文字でも混ざると相手が JSON を読めなくなります。
  捨てないのは、動かないときに何も分からなくなるためです
- **相手がいなくなったら、こちらも終わります。** 残っているとモデルを抱えたまま居座ります

実際の利用例は Omnical AI です。あちらは「ファイルに触れる処理は必ず安全層を通す」という約束を持っているので、
qwc は道具を持たないまま輪だけを回し、読み書きはあちらの安全層が引き受けています。

## いま思考モードがどうなっているか、`/think` で見られます

ここには**別々の2つ**があります。「考えさせるかどうか」と「考えている様子を画面に出すかどうか」です。
どちらも見えないと、切り替えたつもりで切り替わっていないのか、
切り替わったが画面に出ていないだけなのかが分かりません。`/think` だけ打つと、いまの状態が出ます。

```
❯ /think

  考えさせる　　 はい
  考えている様子 1行だけ出す
  変えるには: /think on | off | compact | full | quiet
```

- **引数なしは「見るだけ」です。**以前はここで思考モードが入っていて、見るつもりで打つと勝手に切り替わっていました
- 変えたあとも、同じ表示が出ます。**効いたかどうかを、その場で確かめられます**
- `/think quiet` を足しました。**考えさせるが様子は出さない**、という組み合わせに対話中から戻せませんでした

> **希望どおりになるとは限りません。**モデルが思考モードを持たなければ、指定しても無効になります。
> 以前は「入れました」とだけ出していたので、その場で嘘になっていました。
> いまは**実際に効いている値**を出し、食い違っていれば理由を添えます。

## 考える深さを選べます（`/effort`）

思考は「入れる／切る」の2択ではありません。**問題によって、考える価値が桁で変わります。**
2026-09-03 に gemma4:26b で測った結果がこれです。

| 問題 | 考えない | 考える | どちらが正しかったか |
|---|---|---|---|
| 道具を選ぶ（4問） | 4tok / 0.46秒 | 74〜85tok / 2.3〜2.5秒 | **4問とも答えが同一** |
| 論理（guard の判定バグ） | 42tok / 1.3秒 | 1147tok / 31.2秒 | **考えたほうだけ正解** |
| 計算 | 327tok / 9.1秒 | 1927tok / 53.2秒 | 考えたほうが完答 |

`read_file` を選ぶだけの場面で毎回250字考えるのは、1手あたり約2秒の丸損です。
逆に筋道の要る問題で切ると、**間違った答えが速く返ってくるだけ**になります。

```
❯ /effort

  ○ off     考えない  道具を選ぶだけの作業。実測で約5倍速い
  ○ low     浅く      手順が決まっている作業
  ● medium  ふつう    既定
  ○ high    深く      上限なし。素の深さで考える（実測で medium の3.4倍の時間）

  ollama に送る think medium
  指示文に足す一文　 考えるときは5文以内にまとめること。
```

**深さの効かせ方は2つあり、モデルによって効く側が違います。**

1. ollama の `think: "low"|"medium"|"high"` … 段階を持つモデルだけ
2. 指示文の末尾に足す一文 … 言うことを聞くモデルだけ

`gemma4:26b` で両方を測りました（同じ問題・temp=0・2回ずつ）。

| | 結果 |
|---|---|
| **① ollama の段階** | **まったく効かない。** `low` が 3183字と3961字、`high` も 3183字と3961字。**同じ段階で違う出力が出て、違う段階で同じ出力が出る** |
| **② 指示文の一文** | **よく効く。** 下表のとおり |

| 足した一文 | 思考 | 生成 | 時間 | 答え |
|---|---|---|---|---|
| （なし） | 3183字 | 1147tok | 37.0秒 | 正解 |
| **「2文以内」** | **1022字** | **370tok** | **13.2秒** | **正解のまま** |
| 「5文以内」 | 1178字 | 403tok | 10.8秒 | ほぼ正解 |
| 「徹底的に」 | 3196字 | 1235tok | 33.3秒 | **深くならず、形だけ壊れた** |

**効くのは「短くしろ」だけで、「深く考えろ」は効きませんでした。** 最後の行が大事で、
「可能性を列挙して検討せよ」と足しても思考量はほぼ変わらず（3183→3196字）、
答えだけが箇条書きに化けて「一文で」という指示を踏み潰しました。**足して悪くなるものは足しません。**

だから段は「**考える長さの上限**」として並べてあり、`high` はその上限を外した状態＝モデルの素の深さです。
どちらの効かせ方が働いているかは断言できないので、`/effort` は**送っている中身をそのまま**出します。

> **深さの持ち主は `config.effort` ひとつだけ**にしてあります（`src/effort.mjs`）。
> 持ち主を2つにすると `/think off` と `/effort high` が互いを打ち消し、
> どちらが効いているのか誰にも分からなくなります。`--no-think` と `/think off` も、いまは effort に書きます。
>
> ```
>   考えさせる　　 いいえ
>   ※ qwen2.5-coder:14b は思考モードを持たないので、考えさせる指定は効きません。
> ```

## 「いい感じにして」でも止まりません

**どこを直すか書いていない依頼**が、いちばん詰まりやすい形でした。実測した壊れ方はこうです。

- 28ファイルのプロジェクトに「画面が見にくいから、いい感じにして」と頼む
- 同じ `App.tsx` を3回読み直しながら**7分ぶん読み続ける**
- ファイルを丸ごと書き直そうとして 176行の差分を作り、文脈が膨れる
- 最後は**空の返事**を返し、**画面に1文字も出さずに終わる**

利用者から見れば「アバウトに頼むと何も起きない」です。3つで止めています。

**1. 空の返事で黙って終わりません。**
空を弾く処理が「最初の1手」にしか掛かっていませんでした。いまはどの時点でも促し、
それでも空なら**何が起きたかを日本語で伝えて**終わります。黙って終わるのが一番たちが悪いためです。

**2. 調べるばかりで進まないとき、区切りを入れます。**
道具を10回使って何も変わっていなければ、1度だけこう促します。

```
調べるばかりで先に進んでいないので、区切りを促しました。
```

出口は3つ示します。**小さく直す／答える／1つだけ聞く。**
ここで「変更しろ」とだけ言ってはいけません。**ただ質問しただけの人のファイルを触ってしまう**ためです。

**3. 曖昧な依頼への向き合い方を指示文に書きました。**
まず絞り込む。ひとつに絞れたら**いちばん小さい変更**を入れて報告する。
どうしても分かれるときだけ、見つけた候補をファイル名つきで並べて**1つだけ**聞く。
**丸ごと書き直すことは禁止**にしました（誰も確認できない差分になり、頼まれていないものまで変わるため）。

直したあと、同じ依頼はこうなりました。

```
● read_file ×3 … ● 調べるばかりで先に進んでいないので、区切りを促しました。
● edit_file(src/App.tsx)

src/App.tsx のヘッダーに shadow-sm を追加して、コンテンツとの境界をより明確にしました。
```

**変更は2行**です（以前は176行の全面書き換えでした）。

## ↑ で前に打った依頼を呼び出せます

`↑` `↓` で履歴をたどれます。**終了しても残ります**（`~/.qwythos-code/history`・200件まで）。
同じ作業を翌日に続けることが多く、毎回打ち直すのは無駄なためです。

> **承認の答えは履歴に入れていません。**`y` `n` `a` も同じ入力欄を通るので、
> そのままだと `↑` を押しても `y` しか出てこず、**履歴が使い物になりませんでした**。
> 残すのは本人が打った依頼だけにして、それ以外は読んだ直後に履歴から抜いています。

## 置き換えに失敗したとき、同じ失敗を繰り返しません

`edit_file` は `old_string` がファイルと**一字一句そろっていないと通りません**。
手元のモデルはここで外しやすく、外すたびに少しずつ違う書き方で作り直しては、また外します。
引数が毎回わずかに違うので、同じ呼び出しを止める仕掛けでは捕まりません。

実機では、808行の `Sidebar.tsx` を相手に **83.9秒の思考をはさんで同じ失敗を続ける**ことがありました。

2つで止めています。

**1. 狙った場所の現物を返します。**
以前はファイルの先頭80行を返していました。長いファイルでは**直したい場所がそこに入っておらず**、
手がかりの無いまま推測を重ねることになります。いまは、送られてきた `old_string` に
**いちばん近い場所を探して、その周りだけ**を行番号つきで返します。

```
old_string was not found in the file. It must match the file text exactly.
The closest place is around line 648 (4 of your 5 lines appear there).
Here is what the file actually contains there. Copy from this, without the line numbers:
```

半分も重ならない場所は返しません。**見当違いの場所を「ここです」と言うと、
モデルはそれを信じて別の間違いを重ねます。**そのときは「別のファイルを見ているかもしれません」と伝えます。

**2. 2回続けて外したら、やり方ごと変えさせます。**
「その道はもう通らない」と伝えて、**現物の全文を渡し、`write_file` で丸ごと書き直させます**。
一度通れば数えは振り出しに戻ります。

400行を超えるファイルでは丸ごと書き直させません（別の壊し方になるため）。
そのときは `read_file` に `offset` と `limit` を付けて、**いま読んだ範囲からだけ写す**よう促します。

## 書いた中身が画面に出ます

書き換えたら、**何をどう変えたのかがその場に出ます。**

```
● edit_file(price.js)
  ⎿ 1 か所を置き換え
     3    return price * 1.10;
     4  }
     5
     6 +// 税抜き価格を出す
     7 +export function withoutTax(price) {
     8 +  return price / 1.10;
     9 +}
```

新しく作ったときは、書いた中身がそのまま出ます。

```
● write_file(test_price.js)
  ⎿ 新規作成 (13 行)
     1 +import { withTax } from './price.js';
     2 +
     3 +const price = 100;
```

- 出るのは `write_file` と `edit_file` だけです。読むだけの道具では出しません
- **確認欄で既に見せているときは、重ねて出しません。**`--yolo` で確認を飛ばしているときほど、ここが唯一の手がかりになります
- 長い変更は途中で省きます（差分は40行、新規作成は20行まで）
- 消したいときは `~/.qwythos-code/config.json` に `"showDiff": false`

> **作るのは実行より先です。**書き換えたあとでは元の中身がもう無く、差分を作れません。
> 実行前に作っておいて、確認を出さなかったときだけ実行後に出しています。

## 書き換えを取り消す（`/undo`）

直前のお願いでした書き換えを、まとめて元に戻します。

```
❯ /undo
  ✓ cart.js を元に戻しました
```

**戻す単位は「1手」ではなく「1回のお願い」です。** モデルは1回のお願いで3ファイルを直すことがあり、
そのうち1つだけ戻しても、コードは半端な状態で残ります。同じお願いのぶんは、まとめて戻します。

同じファイルを何度直していても、報告は1行にまとめます。3回直したから3行出す、では
別々のファイルと見分けが付かなくなるためです。

### そのあと自分で触ったファイルには、手を出しません

いまディスクにある中身が、こちらが書いた中身と違うなら、間に誰かが入っています。
そこを巻き戻すのは他人の作業を消すのと同じなので、理由を添えて飛ばします。

```
❯ /undo
  ✓ src/app.js を元に戻しました
  ! src/config.js はそのままにしました — そのあとで別に書き換えられています
```

### 戻したことは、モデルにも伝えます

黙って戻すと、モデルは直したつもりのまま次の一手を組み立て、同じ書き換えをもう一度します。
`/undo` のあとは「その変更はもう無い。直す前に読み直せ」と伝えます。

### 戻せないもの

- **`run_command` が変えたもの。** シェルの中で何が起きたかは分からないので、控えが取れません
- **読めない形式のファイル**（画像など）。控えを持たないぶん、戻せないと伝えて手を出しません
- **`/clear` より前のもの。** 会話をまっさらにしたのに前の作業が戻せると、
  画面に何も残っていないぶん、何が起きたのか分からなくなります
- 控えは直近 **60回ぶん**、1ファイル **2MB** までです

> **git があるならそちらが確実です。** `/undo` は、git を使っていないフォルダや、
> まだコミットしていない範囲を戻すためのものです。

## 変更をまとめて見る（`/diff`）

そのセッションで書き換えたぶんを、**始める前と今の違い**として並べます。

```
❯ /diff

● cart.js 変更
     1  const total = (items) => items.reduce((a, b) => a + b.price, 0);
     2 +const totalWithDiscount = (items, rate) => total(items) * (1 - rate);
```

途中の経過ではなく通しの差分です。3回直したファイルを3回ぶん見せられても、
結局どうなったのかは分かりません。知りたいのは始める前と今の違いだけです。

`/diff src/app.js` のように書けば、そのファイルだけを見られます。
ファイル名だけでよければ `/files` です。

## 何にどれだけ待たされたかが見える

応答のたびに、かかった時間の内訳が1行出ます。

```
  ⏱ 11.9s  読み込み 0.2s / 前処理 0.2s・4,554 tok / 生成 11.5s・35.0 tok/s
```

**ローカルでは、待ち時間の大半が生成ではないところで消えます。** モデルの読み込み（冷えていると分単位）と、
送った会話を読む前処理です。合計の秒数だけ見せても、文脈を広げすぎたのか、
モデルが GPU に載り切っていないのかを切り分けられません。

- **2秒未満の応答には出しません。** 1手が2秒で終わる作業に毎回内訳が付くと、ただの雑音になります
- 常駐していれば「読み込み」の行は出ません（0秒なので）
- 止めるには `~/.qwythos-code/config.json` に `"showTiming": false`

通しの合計は `/stats` で見られます。

```
❯ /stats

  やり取り      1 回
  ツール実行    16 回
  入力トークン  72,194
  出力トークン  2,312
  会話の長さ    36 件

  モデルを待った時間  78.0 秒
    うち読み込み      3.2 秒
    うち前処理        9.2 秒 （送った会話を読む時間）
    うち生成          65.5 秒（35.3 tok/s）
```

（実測値です。16回の道具の往復で入力が72,194トークンあるのは、**会話を毎回まるごと送り直している**ためです。
前処理の9.2秒はその代金にあたります。`spawn_agent` に調べさせて答えだけ受け取ると、ここが軽くなります）

### 待たされているあいだ、何が起きているかを出します

```
⠹ 考えています 3/40手め (18s) — まだ1文字目が来ていません
```

何手目かを添えるのは、進んでいるのか同じ所を回っているのかを見分けるためです。
45秒を超えると「モデルの読み込みか前処理の途中です」に変わります。
どちらも「固まった」ではないと分かるだけで、待てるようになります。

## 打ちやすくする工夫

### Tab で補完する

`@src/agent.mjs` のように、**正確に打たないと効かない**入力が増えました。1文字違うと `@` は黙って
素通しし、モデルは自分で `search_files` から探し直します。打ち間違いの代償が
「往復2回ぶん遅くなる」ことなので、そもそも打たせないほうが早い、という考えです。

補完するのは3つだけです。

| 打っているもの | Tab で出るもの |
| --- | --- |
| `/mod` | `/model`（自分で作った `.qwythos/commands` のぶんも） |
| `/model gem` | `gemma4:26b`（入っているモデルの名前） |
| `@src/ag` | `@src/agent.mjs`（作業フォルダのファイルとフォルダ） |

ふつうの日本語を打っている最中には、何も出しません。候補が出るほうが邪魔だからです。

作法は bash と同じで、候補が複数あるときは **1回目で共通部分まで入り、2回目で一覧が出ます**。
フォルダは末尾に `/` を付けて返すので、そのまま次を打ち始められます。
何も打っていない状態では `node_modules` や隠しファイルは出しません（自分で打てば出ます）。
作業フォルダの外は補完しません（出したところで `@` が受け取りません）。

### 複数行を貼り付けても、エンターを押すまで送りません

複数行を貼ると、端末は改行のたびに1行ずつ送ってきます。readline はそれを「本人がエンターを押した」と
受け取るので、そのままだと**10行のエラーログを貼っただけで、押していないのに依頼が飛びます**。
しかも飛ぶのは1行目だけで、残りは順番待ちに積まれます。

そこで端末に**貼り付けの印**（bracketed paste）を出させ、印と印のあいだの改行は行の確定として扱いません。
貼った中身は入力欄に置かれるだけで、送るのは本人がエンターを押したときです。

複数行のときは、入力欄には札が置かれます。中身は控えてあり、エンターを押した時点で元に戻します。

```
❯ [貼り付け1: 3行] を直して
  3 行を、1つの依頼としてまとめて受け取りました。
```

札にするのは複数行のときだけです。1行だけ貼ったとき（パスや URL）は、打ったのと同じようにそのまま入ります。
行を丸ごとコピーすると末尾に改行が付いてきますが、これは「送れ」の合図ではないので落とします。

貼り付けの中の `Tab` は補完を起こさず、字下げのまま残ります。長すぎる貼り付けは 100,000 文字で切り、
切ったことをその場で伝えます。

印は端末が付けるものなので、`qwc` 側では入力を待つたびに印を出す合図をかけ直します
（道具で走らせた `vim` などが終わると消えることがあるため）。終わるときは必ず消すので、シェルには残りません。

**印に対応していない端末むけの保険も残してあります。** 確定してしまった行は、続けざまに届いたかどうか
（15ミリ秒）で1つにまとめ直します。送信そのものは止められないので、あくまで次善の策です。

**まとめるのは端末のときだけです。** パイプで流し込まれた入力（`printf ... | qwc`）は全行が同じ瞬間に届くので、
ここでまとめると台本が丸ごと1つの依頼に化けます。

### `@` でファイルを渡す

場所が分かっているなら、探させずに直接渡したほうが速く、間違いません。

```
❯ @src/agent.mjs の runTurn を短くして
  @src/agent.mjs を添えました（18,204文字）
```

**道具の往復が2回減ります**（`search_files` → `read_file` を省ける）。実測で、
渡したときは道具を1度も呼ばずに答えました。

作業フォルダの外（`@../../.ssh/id_rsa` など）は断ります。読めなかったものは理由つきで出すので、
黙って無視されることはありません。

### `@` で画像も見せられる

スクリーンショットをそのまま渡せます。**目を持つモデル**（`gemma4:26b` など）が要ります。

```
❯ @screen.png この画面に何が写っているか3行で教えて
  @screen.png を画像として見せます（428KB）

「Omnical AI」という、AIを使って様々なタスクをこなすためのインターフェース画面です。
中央には質問や要約、メール作成、思考の整理といった機能が配置されています。
左側には、フォルダ管理、読み込んだ書類、保存した会話などのツールメニューが並んでいます。
```

（実際のスクリーンショットで確認した出力です）

目のないモデルのときは、送らずに理由を出します。

```
! @screen.png は渡せませんでした（いまのモデルは画像を見られません（-m gemma4:26b などで試せます））
```

対応するのは `.png .jpg .jpeg .gif .webp .bmp`、1枚 8MB まで。
**画像は直近の1発言にだけ残します**（1枚で文脈をかなり食うため、古いものは自動で落とします）。
会話の記録にも中身は保存せず、「画像を見せた」という事実だけを残します。

### `/名前` で決まった依頼を呼ぶ

`.qwythos/commands/名前.md` を置くと `/名前` で呼べます。中身がそのまま依頼になります。

```markdown
<!-- .qwythos/commands/review.md -->
# 変更を見直す
直近の変更を確認して、抜けている検証と危ないところを指摘してください。
$ARGUMENTS
```

```
❯ /review 認証まわりを重点的に
  /review — 変更を見直す
```

`$ARGUMENTS` に引数が入ります（書き忘れた場合は末尾に足されます）。1行目の見出しは説明として使われ、
本文からは外れます。`~/.qwythos-code/commands/` に置けばどのプロジェクトからでも使え、
同じ名前なら作業フォルダ側が優先されます。一覧は `/commands`。

### モデルは入っているものから選びます

指定されたモデルが無いとき、エラーで止まらずに、入っているものから妥当なものを選びます
（埋め込み専用は除外）。既定は `gemma4:26b` です。

> **大きさと速さは比例しません。** 同じ作業（5手のテスト修正）で **9B は30秒、14B は10分超**でした。
> 一方 `gemma4:26b` は 26B ですが MoE で実効3.8Bなので、9B より速く動きます。
> 選ぶ基準は大きさではなく実測です（→「モデルの癖への対処」）。

### 実測で比べたモデル

| モデル | 1手あたりの思考 | 完走 | 画像 | 備考 |
| --- | ---: | :---: | :---: | --- |
| **`gemma4:26b`（MoE）** | **0.6〜3秒** | ✅ | **✅** | **既定。**速さも正しさも一番。18GB 必要 |
| `qwythos:latest`（9B） | 3〜9秒 | ✅ | ✗ | 7.4GB と軽い。メモリが足りないとき用 |
| `qwen3:14b-q4_K_M` | 遅い | △ | ✗ | 5手の作業が10分超で終わらず |
| `qwen2.5-coder:14b` | ― | △ | ✗ | 道具を呼ばず本文にJSONを書く（対策済み） |

#### gemma4:26b を既定にした理由（2026-08-07 の実測）

同じ課題（既存の `total` を使い回して `totalWithDiscount` を足す）を両方に投げました。

| | `qwythos:latest`（9B） | `gemma4:26b` |
| --- | --- | --- |
| かかった時間 | 46.5秒 | **36秒**（18GB の読み込み込み） |
| 書いたコード | **壊れていた**（`items` を受け取らないのに `total()` を引数なしで呼ぶ） | **正しい** |
| 無駄な手数 | 存在しないパスを3手ぶん試して約24秒 | なし。自分からやることリストも作った |

**メモリが足りない環境では `-m qwythos:latest` に落としてください。**7.4GB で動きます。

### メモリが足りないときは自動で軽いモデルに落とします

起動時にモデルを読み込み、**GPU に丸ごと載ったかを確かめます。**載りきらないと、はみ出した分は
CPU 側で動いて極端に遅くなりますが、画面には何も出ません。「今日はなぜか遅い」の正体がこれです。

載りきらなかったときは、こう出して `qwythos:latest`（7.4GB）に切り替えます。

```
! gemma4:26b は GPU に 46% しか載りませんでした（残りは CPU 側で動くため極端に遅くなります）。
  qwythos:latest に切り替えます。GPU の空きが戻れば、次回はそのまま gemma4:26b を使います。
  このまま使いたいときは -m gemma4:26b を付けてください。
```

- **切り替えるのは容量が足りないときだけです。**作業の内容では切り替えません
- **`-m` で指定したときは落としません。**本人が選んだものを黙ってすり替えないためです
- Ollama に聞けなかったときも落としません。確かめられないことを理由に、使えるものを取り上げません
- 切ることもできます（`~/.qwythos-code/config.json` に `"autoDowngrade": false`）

> **なぜ「作業の重さ」で切り替えないのか。** 実測すると、軽いほうが遅いからです。
> `gemma4:26b` は **40.7 tok/s**、`qwythos:latest`（9B）は **18.1 tok/s**。
> 26B ですが MoE で実効3.8Bなので、9B より 2.2倍速く動きます。書くコードの正しさでも勝っています。
> **速さでも正しさでも負けているモデルに切り替える理由がありません。**
>
> なお2つのモデルは同時に載りません（17.3 + 7.9 = 25.2GB で GPU枠を超える）。
> 片方を載せると、もう片方は追い出されます。切り替えの往復は 3〜7秒です
> （ディスクから初めて読むときだけ 81秒かかります）。

> `gemma4:26b` は日本語で頼んでも英語で返してきました。指示文の**末尾**に言語の念押しを
> 置いて直しています（指示は最後にあるものほど効きます）。

## やることリストと計画モード

長い作業になると、小さいモデルは途中で「何を頼まれていたか」を見失います。
段取りを紙に書き出させて、そこへ何度でも戻れるようにしてあります。

### やることリスト

3手を超える作業では、モデルが自分でリストを作って進めます。

```
● やること (1/3)
  ☑ b.js の引き算を足し算に直す
  ▸ c.js の引き算を足し算に直す
  ☐ npm test 実行
```

いま手をつけているものだけが太字になります。`/todo` でいつでも見返せます。

> **頼むだけでは呼びません。** 実測（qwythos 9B）で、5手で終わる作業では
> 指示しても `todo_write` を呼びませんでした。短い作業ならそれで困らないので放っておき、
> **道具を6回使ってもリストが無いときだけ、1度だけ促します**。
> 促したあとは自分で更新しながら最後まで走りました。毎回促すと、そのぶん往復を食って本来の作業が進みません。

### 計画モード

いきなり書き換えられると困るときは、先に方針だけ出させます。

```
❯ /plan
  ✓ 計画モードに入りました。
    書き換えとコマンド実行の道具を外しました。まず調べて、方針を出します。

❯ 認証まわりをリファクタしたい

（調べたうえで方針を出す）

┌ この方針で進めますか
└ y = 実行に移る / n = このまま相談を続ける
```

`y` を押すと道具が戻り、その方針のまま実行に移ります。`n` なら計画モードのまま相談を続けられます。

**「使わないでください」と頼むのではなく、道具そのものを外しています。** `write_file` と `edit_file` は
モデルに渡らず、`run_command` も読み取り専用のものしか実行しません。頼むだけでは、小さいモデルは守りません。

`--plan` を付けて起動すれば、最初から計画モードで始まります。

### 雑談と作業を見分ける

`qwc` と打って立ち上げれば、雑談も作業も同じ画面でできます。何も切り替える必要はありません。

```
❯ そういえば消費税っていま10%だよね。昔は8%だったのになあ。
  雑談として受け取ります（雑談の言い方）。書き換えるときは確認します。

  そうですね、以前は8%の時期もありましたが、現在は10%ですね。時代の変化を感じます。

❯ tax.js の税率を10%にして

  ● read_file(package.json)
  ● edit_file(tax.js)
  tax.js の税率を 8% から 10% に変更しました。
```

上は両方 `--yolo`（確認なし）で、同じフォルダで続けて打ったものです。前者ではファイルに指一本触れず、
後者ではそのまま書き換えています。

**なぜ要るのか。** 作業用の指示文には「問題を指摘されたら直せ」が入っています。作業中は正しい態度ですが、
雑談では困ります。この機能を入れる前、上と同じ独り言を言ったらこうなりました。

```
❯ そういえば消費税っていま10%だよね。昔は8%だったのになあ。

  tax.js の消費税率を 8% から 10% に更新しました。
  ✓ 書き換えたファイル (2 件)  test_tax.js  tax.js
```

**どう見分けているか。** モデルには聞きません。言葉づかいだけを見て、その場で決めています。

モデルに聞くと1往復ぶん待たされるうえ、発言ごとに指示文や道具の一覧を入れ替えることになり、
そのたびに会話を丸ごと読み直します（実測：入れ替えないと 4,923 トークンを 0.3 秒で通るところが、
入れ替えると 1,402 トークンで 2.0 秒かかりました）。判定はその場で終わらせ、いちばん上は一切動かさず、
結果は**発言の末尾に一言添えるだけ**にしてあります。待ち時間は増えません。

見分け方は上から順に、こうなっています。

| 見るもの | 例 | 結果 |
| :--- | :--- | :--- |
| コードの貼り付け・長い文 | ```` ```js … ``` ```` | 作業 |
| 依頼の言い方 | 「直して」「合わせて」「揃えてくれる？」「fix …」 | 作業 |
| 疑問形 | 「この設計どう思う？」「tax.js ってどうなってる？」 | 雑談 |
| 雑談の言い回し | 「〜だよね」「なるほど」「お疲れさま」 | 雑談 |
| 作業の名指し | 「ログイン機能の追加」 | 作業 |
| ファイルの名指し | 「src/app.js の話」 | 作業 |
| どれでもない | 「うーん」「疲れた」 | 雑談 |

**外したときにどうなるかで、順番を決めています。**

- 雑談を「作業」と間違える → 頼んでいないのにファイルが書き換わる（実害あり）
- 作業を「雑談」と間違える → 手を出す前に一度確認が出るだけ（`y` を押せば進む）

損得が左右でまったく違うので、迷ったものは雑談側に置いてあります。
「tax.js の税率、古いままだなあ」はファイル名を出していますが、頼んではいないので雑談です
（最初はファイル名を優先していて、実機で黙って書き換わりました）。

**外したときの受け皿。** 雑談と見た発言の途中でモデルが書き換えようとしたら、その場で聞きます。

```
❯ tax.js の税率、古いままだなあ
  雑談として受け取ります（雑談の言い方）。書き換えるときは確認します。

  ● read_file(tax.js)
  ● edit_file(tax.js)

┌ 作業として進めますか
│ 雑談だと思って受け取りましたが、edit_file を使おうとしています。
└ y = 作業として進める / n = 答えるだけにしてもらう
  → [y/n] うん

  ⎿ 1 か所を置き換え
     2 -const TAX_RATE = 0.08;
     2 +const TAX_RATE = 0.1;
```

`y`（「うん」「はい」でも通ります）なら、その発言は作業だったものとして最後まで進み、以後この発言では聞きません。
`n` なら書き換えず、言葉で答えます。**確認なしモード（`--yolo`）でも、この確認だけは出ます。**
あれは「頼んだ作業を任せる」という意味であって、頼んでもいない雑談で書き換えてよいという意味ではないからです。
`-p`（一回だけ実行）では答えられないので、書き換えない側に倒れます。

雑談と見たときは、読む道具（`read_file` `search_files` `list_dir`）とネットの道具はそのまま使えます。
話の流れで「あのファイルどうなってた？」と聞けるようにするためで、読むだけなら外しても実害がありません。
「手を動かしていないぞ」と促す仕組みも、雑談のあいだは止まります。あれは作業を頼まれている前提の催促で、
そのままだと頼まれてもいないことを無理にやらせてしまいます。

### 雑談モード

ずっと雑談をするなら、モードごと切り替えられます。自動の見分けより強く、書き換える道具そのものを外します。

```
❯ /chat
  ✓ 雑談モードに入りました。
    書き換えの道具を外し、指示文も雑談用に差し替えました。作業に戻るときは、もう一度 /chat。

雑談 ❯ そういえば消費税っていま10%だよね

はい、標準税率は10%です。ただ、食品や飲料などの一部の品目には8%の軽減税率が
適用されるので、買い物をする時は両方の税率が混ざっていますよね。

雑談 ❯ /chat
  ✓ 雑談モードを抜けました。ここからは作業モードです。

❯ じゃあ tax.js の税率もそれに合わせて

（tax.js の TAX_RATE を 0.08 → 0.10 に書き換える）
```

**会話は切れません。** 差し替えるのはいちばん上の指示文だけで、それまでのやり取りは残ります。
上の例で「それに合わせて」が通じているのは、雑談モードで話した10%をそのまま覚えているからです。

**なぜモードを分けるのか。** 作業用の指示文には「問題を指摘されたら直せ」「変えるべきと書きそうに
なったら手を動かせ」が入っています。これは作業中には正しい態度ですが、雑談では困ります。
実際、上と同じ独り言を作業モードで言うと、こうなりました。

```
❯ そういえば消費税っていま10%だよね。昔は8%だったのになあ。

  tax.js の消費税率を 8% から 10% に更新しました。
  ✓ 書き換えたファイル (2 件)  test_tax.js  tax.js
```

頼んでいないのに書き換わり、確かめるためのファイルまで増えています。
「いまは雑談です」と足すだけでは足りず、人格ごと入れ替える必要がありました。

雑談モードでは、こうなります。

- `write_file` と `edit_file` はモデルに渡りません。`run_command` も読み取り専用のものだけです。
- `todo_write`・`spawn_agent`・`find_symbol`・`read_skill` も渡しません。どれも作業のための道具です。
- 読む道具（`read_file` `list_dir` `search_files`）とネットの道具は残ります。
  話の流れで「あのファイルどうなってたっけ」と聞けます。
- `QWYTHOS.md` やプロジェクトの調査結果を積みません。指示文が **3,136 → 1,402 トークン**に減り、
  前処理が 5.2 秒から 2.0 秒になりました（gemma4:26b で実測）。

`--chat` を付けて起動すれば、最初から雑談モードで始まります。計画モードとは同時に入れません
（あとから入れたほうが残ります）。どちらのモードも保存されないので、次の起動は作業モードからです。

打ちこむ場所の左に、いまのモードが出ます（`雑談 ❯` ・ `計画 ❯` ・作業中は `❯` だけ）。
切り替えたときの一行が流れて見えなくなっても、その一言が作業の指示として受け取られるのかが分かります。

## ネットにつながる部分

手元のモデルは学習した時点までのことしか知りません。ライブラリの新しい版・見たことのないエラー・
API の細かい仕様は、調べたほうが確実です。そのための道具が3つあります。

### 何が出ていくか

| 道具 | 出ていくもの |
| --- | --- |
| `web_search` | 検索の言葉だけ |
| `web_fetch` | URL だけ |
| `browse` | URL と、**そのサイト向けに保存済みの Cookie**（ログイン状態を使うため） |

**どの道具でも、ファイルの中身・会話の履歴・作業フォルダの場所・鍵は送りません。**
外に出る処理は `src/web.mjs`（検索・取得）と `src/browser.mjs`（ブラウザ）の2ファイルだけなので、
そこを読めば全部確かめられます。

### 使う前に必ず聞きます

ネットに出る3つは、書き換えと同じく**実行前に確認**します。何を検索するか・どこを開くかが
画面に出てから決められます。

```
┌ 確認 ネットで検索します
│   Node.js 24 fetch stable
│   この言葉が検索サービス（Tavily）へ送られます
└ y = 実行 / n = やめる / a = 以後このセッションは同種を自動許可
```

`a` を押せば、そのセッション中は聞かれなくなります。`--no-net` を付けて起動すれば、
道具そのものを渡さないので、モデルは存在すら知りません。

### 手元や社内のアドレスは読みません

`web_fetch` は公開されたページ専用です。次は断ります。

- `localhost` / `127.0.0.1` / `::1`
- 私有アドレス（`10.x` / `172.16〜31.x` / `192.168.x`）
- リンクローカル `169.254.x`（**クラウドの資格情報が置いてある場所**）
- `.local` / `.internal` で終わる名前
- `http` `https` 以外（`file://` など）

転送（リダイレクト）された先も、最後にもう一度調べます。指示文に URL を書くだけで
手元のサービスを叩かせる、という筋を塞ぐためです。

## ログインが要るサイトを読ませる

社内 Wiki、GitHub の非公開リポジトリ、管理画面。`web_fetch` ではログイン画面しか取れません。
そういうページは、**あなたが普段使うのと同じ本物のブラウザ**で開きます。

### やりかた

```
❯ /login github.com

  ブラウザを開きます。表示された画面で、いつも通りログインしてください。
  qwc はパスワードを受け取りません。終わったらここで Enter を押してください。
  → ログインが終わったら Enter
  ✓ github.com のログイン状態を保存しました（Cookie 14 件）。
```

以後は、頼むだけで読めます。

```
❯ このPRの説明を要約して https://github.com/…/pull/12

● browse(https://github.com/…/pull/12)
  ⎿ Fix the retry loop by …
```

| コマンド | 何をするか |
| --- | --- |
| `/login <サイト>` | ブラウザを開いて手でログインし、その状態を保存する |
| `/logins` | ログイン状態が残っているサイトの一覧（値は出しません） |
| `/logout` | 保存したログイン状態をすべて消す |

### パスワードは受け取りません

**qwc はパスワードを保存しません。求めもしません。** 入力するのは本物のブラウザの画面で、
qwc はそのキーボード入力にも画面の中身にも触りません。

残るのは `~/.qwythos-code/browser/`（`700`）で、中身はブラウザが管理する形の Cookie と
localStorage です。これは**あなたのログイン済みセッションそのもの**なので、
共用のパソコンでは使い終わったら `/logout` してください。

### 自動化と気づかれないようにしています

画面なしのブラウザは、既定では「自動で動かしています」と自分から名乗ります
（`navigator.webdriver` が `true`、UA に `HeadlessChrome`）。
これを見て**ログインし直しを迫るサイトがある**ため、名乗りだけをふつうのブラウザに揃えてあります。

| | 直す前 | 直した後 |
| --- | --- | --- |
| `navigator.webdriver` | `true` | `false` |
| UA | `HeadlessChrome/151…` | `Chrome/151…` |

あなた自身のブラウザで、あなた自身のアカウントの、あなた自身のページを開くためのものです。
**それでも見破って断るサイトはあります**し、サイトの利用規約に反する使い方をしてよいという意味でもありません。

### 残るログイン・残らないログイン

実測で確かめた挙動です。

| 種類 | ブラウザを閉じたあと |
| --- | --- |
| 有効期限つき Cookie（「ログインしたままにする」） | **残ります** |
| localStorage に入るトークン（最近のWebアプリ） | **残ります** |
| セッション Cookie（期限なし） | 消えます（ブラウザの仕様） |

3つ目に当たるサイトは、`/login` してもすぐ切れます。そのときは使うたびに `/login` してください。

### `web_fetch` との使い分け

| | `web_fetch` | `browse` |
| --- | --- | --- |
| 速さ | 速い（0.2秒程度） | 遅い（1〜2秒＋起動） |
| ログイン | 使えない | **使える** |
| JavaScript で描くページ | 読めない | **読める** |
| `localhost` / 手元の開発サーバー | 断る | **開ける** |

公開ページは `web_fetch` を先に使うようモデルへ指示してあります。`browse` は、
それで足りなかったときの手段です。

> `browse` が手元のアドレスを開けるのは意図した違いです。`localhost:3000` の画面を
> 見てもらう用途が実際に多いためです。開く前に必ず URL を見せて確認します。

### 用意するもの

ブラウザ操作にだけ Playwright が要ります。**入っていなければ `browse` はモデルに渡らず**、
それ以外の機能はそのまま動きます。

```bash
cd ~/コーディングCLI
npm install playwright && npx playwright install chromium
```

### 検索の鍵

`web_search` には Tavily の鍵が要ります。次のどちらかで用意してください。

```bash
export TAVILY_API_KEY=...            # 起動するシェルに置く
# または
echo 'TAVILY_API_KEY=...' > ~/.qwythos-code/.env && chmod 600 ~/.qwythos-code/.env
```

**鍵が無いときは `web_search` をモデルに渡しません。** 呼べない道具を見せて失敗させないためです
（`web_fetch` は鍵が要らないので使えます）。他のアプリの設定ファイルは読みに行きません。

## 迷子にならないための工夫

9B という小さめのモデルでも最後まで走り切れるように、輪の側で支えています。

- **同じ呼び出しの繰り返しを検知**し、3回目で止めて「別の手を考えて」と差し戻します
- **ツールの出力が長すぎるときは真ん中を省略**して、文脈の枠を食いつぶさないようにします
- **文脈が7割を超えたら**、まず古いツール出力を短くし、それでも足りなければ会話を自動で要約します
- **ツール実行の往復に上限**（既定40回）を設け、無限に走り続けないようにします
- **`edit_file` の失敗は理由つきで返す**ので、モデルが自分で直せます
- **本文に書かれた道具の呼び出しを拾います**（後述）
- **「やります」と言うだけで動かないとき、その場で促します**（既定5回まで）
- **長くなってきたのにやることリストが無ければ、1度だけ促します**（既定6手め）
- **調べものは別のエージェントに任せられます**（`spawn_agent`・読んだ中身は本体に残りません）

## モデルの癖への対処

ローカルのモデルは、道具の使い方に癖があります。実測で見つけたものと、その対処です。

### 道具を呼ばずに本文へJSONを書く

`qwen2.5-coder:14b` は `ollama show` で「tools 対応」と出ますが、実際には決められたタグ
（`<tool_call>`）を付けずにJSONを本文へ書きます。Ollama は解釈できず、道具は永遠に呼ばれません。

そこで本文からJSONを拾います。裸のJSON・` ```json ` フェンス・`<tool_call>`タグ・配列の4形式に対応し、
**ふつうの文章や、知らない道具名は拾いません**（誤って実行しないため）。
一度拾ったモデルでは、以後そのセッション中は本文を出す前に必ず見分けます（画面にJSONを晒さないため）。

**関数を書くような形もあります。** `qwythos:latest` にこちらから道具の名前を出して頼むと、
その名前を `spawn_agent(task="…")` と文章に書き写して手を止めました（実測・2回とも）。
JSONではないので上の受け皿では拾えません。これも拾いますが、**3つとも満たすものだけ**にしています。

1. 行の先頭から始まっている（文の途中で触れただけのものは取らない）
2. 名前がいま渡している道具のもの
3. **引数の名前が、その道具が実際に持っている引数と一致する**

3つめが効きます。`spawn_agent(task=…)` は通り、`これは spawn_agent(便利です)` は通りません。
` ``` ` で囲まれた中も見ません。書き方の例を見せているだけで、実行してほしいわけではないからです。

### 手順を述べるだけで手を動かさない

「まず〇〇します」「次にテストを実行します」と書いて、道具を呼ばずにターンを終えるモデルがあります。
待っていても永遠に動かないので、その場で促します。

判定は**最後の一文**で行います。「直しました。次にテストを実行します。」のように完了報告と次の宣言が
同居することがあり、全文で見ると完了報告に引きずられて「終わった」と誤認するためです。
逆に、正しい完了報告を促してしまうと同じ話を蒸し返すので、そこは促しません。

### 実測（同じ課題・`qwen2.5-coder:14b`）

「テストを実行して、失敗しているなら直して、通ることを確認して」を繰り返した結果です。

| 対処 | 結果 |
| :--- | :--- |
| 何もしない | 道具を呼べず**何も起きない** |
| 本文からJSONを拾う | 3回中1回成功 |
| ＋ 促し（上限2回） | 修正は入るが、確認まで届かない |
| ＋ 促し（上限5回・最後の一文で判定） | **修正 → テスト実行 → 合格の報告まで完走** |

`qwythos:latest`（9B）は、これらの対処なしで同じ課題を2回とも完走しました。
**モデルが大きいほど自律的に動けるとは限りません。**

### 切り詰めたことに気づかない

道具の出力が長いときは、真ん中を省いて前後を残します（既定12,000文字）。
ところが 9B は、その断り書きを読み飛ばして**全部を見たつもりで答えます**。
45KBのファイルを一度に読ませたら、前3分の1だけを見て「該当は2つです」と答えました（本当は6つ）。

そこで断り書きを、何が起きたかだけでなく**次に何をすればよいか**まで書く形に変えました。

```
…[28537 characters omitted from the middle. THIS IS NOT THE WHOLE OUTPUT —
do not conclude anything about the omitted part. If it matters, read it with
offset/limit or narrow your search.]…
```

### 長い文脈で必ず落ちる問題（修正済み）

**いまは `fetch` を使っていないので、300秒で切れることはありません。**以下は、そう作り替えた理由です。

Node に最初から入っている `fetch` は、**応答の1文字目が返るまで300秒で必ず諦めます**。
この値を設定で伸ばす方法は公開されていません。クラウドのAPIなら妥当な線ですが、手元のモデルには短すぎます。

実測では、**12,668トークンの依頼が301秒ちょうどで `fetch failed` になりました**（`UND_ERR_HEADERS_TIMEOUT`）。
**Ollama 側は無事で、こちらが先に諦めていた**だけです。
暖まっていれば前処理は毎秒500トークンほど出ますが、モデルの読み込みや文脈枠の取り直しが挟まると
最初の1文字までが分単位になります。ファイルを1つ読ませれば届く長さなので、少し長い作業をすると踏みます。

そこで、長くなる2か所（`chatStream` と `chatOnce`）だけ `node:http` で投げ直しています。
追加のライブラリは要りません。待ち方は2段階です。

| いつ | 待つ長さ | 考え方 |
| :--- | :--- | :--- |
| 1文字目が出るまで | 15分 | 長い文脈の下ごしらえをしているだけかもしれない |
| 出はじめたあとで途切れたら | 10分 | 途中で止まったのなら、待っても戻らない |

どちらも `Ctrl+C` でいつでも止められます。

> **出はじめたあとの見切りは、当初3分でしたが短すぎました。**
> **Ollama は道具の呼び出しを、書き終えるまで送ってきません。**組み立てているあいだ、
> こちらには1バイトも届きません（実測で、道具を1つ返すだけのやり取りに14秒の無音がありました）。
> 大きなファイルの書き込みなど長い引数だと、その無音がそのまま生成時間になります。
> 実際、Ollama 側では正常に終わっていたやり取りが 1m22s〜4m46s かかっており、
> 3分の見切りは**動いている作業を殺していました**。
>
> なお、**1文字目までの待ちに前処理が含まれます**。HTTP のヘッダ自体が前処理の完了まで返ってこないためです
> （実測: 21,000トークンの会話でヘッダ到着まで50.9秒）。ここは15分の側が見ています。

### 作業の途中でモデルを降ろされる問題（修正済み）

**いまは自分で掛け直すので、途中で消えることはありません。**以下は、そう作り替えた理由です。

**Ollama は、こちらの依頼を処理している最中でもモデルを降ろします。**起こし方は2つあります。

1. 誰かが**同じモデルを別の広さ（`num_ctx`）で呼ぶ**。Ollama にとっては別物なので、先に載っているほうを降ろします
2. 誰かが**別のモデルを呼び、GPU の枠が足りなくなる**

どちらでも、降ろされた側が処理中だった依頼は途中で消えます。こちらに返るのは
`HTTP 500 {"error":"...unexpected EOF"}` の一行だけで、そこまでの前処理は丸ごと無駄になります。

実測（2026-08-31 の朝）: 60秒おきに走る見張りの点検が**広さを指定していなかった**ため、
既定の 32768 で積み直しをかけていました。qwc は 65536 で、37,000トークンの前処理に2分かかります。
**前処理が終わる前に必ず降ろされるので、1手も終われませんでした。**画面には毎回
「Ollama がエラーを返しました (HTTP 500)」だけが出て、作業はそこで終わっていました。

相手を1つずつ直しても、次に増えた道具がまた同じことをします。
**こちらが掛け直せることだけが、相手にそろえてもらわなくてよい対策**なので、`chatStream` と `chatOnce` に入れました。

| 何を | どうする |
| :--- | :--- |
| 掛け直す壊れ方 | 5xx／`unexpected EOF`／接続断（`ECONNRESET` など）＝相手の都合で消されたもの |
| 掛け直さない壊れ方 | 4xx（依頼そのものが悪い）・待ち時間切れ・`Ctrl+C` による中断 |
| 待つ長さ | 3秒 → 10秒 → 30秒（`retryWaitsMs`。積み直しは3秒では終わらない。冷えた26Bの読み込みは実測36秒） |
| 何回まで | 3回（段数を変えれば増減します。空配列なら掛け直しません） |

**一度でも画面に出したあとは掛け直しません。**同じ話が二度流れますし、途中まで組み立てた
道具の呼び出しが二重に走りえます。消えるのはたいてい前処理の最中——つまり1文字も出ていないとき——なので、
そこだけ拾えば実害はほぼ消えます。

掛け直すときは、理由と待ち時間を1行出します。黙って掛け直すと「今日はなぜか遅い」で終わり、
次に同じことが起きても気づけません。

```
! Ollama に依頼を落とされました（... HTTP 500: unexpected EOF）。3秒待って掛け直します（1/3回目）。
```

> **待つあいだのタイマーを `unref` してはいけません。**
> 他に予定が無ければ Node はそのまま終了します。端末では入力が輪をつないでいるので気づきませんが、
> パイプ越し（`qwc-async` ＝ LINE 経由）だと**知らせだけ出して黙って終わる**ことになります。実測でそうなりました。

なお、**根っこを塞ぐのは別の話**です。同じモデルを触る道具（見張りの点検・音声アシスタントなど）は
`num_ctx` をそろえておくべきで、そろえてあれば積み直し自体が起きません。
掛け直しは、そろえ忘れた道具が1つ増えたときの保険です。

会話の記録は `~/.qwythos-code/sessions/` に残ります。`qwc --resume` で続きから再開できます。

## プロジェクトごとの指示

作業フォルダに `QWYTHOS.md`（または `AGENTS.md` / `CLAUDE.md`）があれば、

## 実測（qwythos:latest / Apple Silicon）

- 生成速度: 約17トークン/秒
- **前処理（送った文を読む速さ）: 暖まっていれば毎秒500トークンほど**
  （2,059トークンで4.0秒。同じ相手に続けて聞けば2回目は0.4秒＝前の分は覚えている）
- 初回のモデル読み込み: 約81秒（以後は `keep_alive` で30分常駐するため待ち時間なし）
- 「2ファイルにまたがる関数追加 → テスト実行 → 失敗を自力修正 → 合格」までを、
  ツール実行9回・約2分で完走することを確認済み

**待たされるときは、たいていモデルの読み込みです。** 生成も前処理も上の速さで出ているのに
体感が遅いなら、直前に別のモデルを使ったか、しばらく空いて常駐が切れたかを疑ってください。
